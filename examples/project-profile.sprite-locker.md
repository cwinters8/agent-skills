# Project profile

Sprite Locker's overlay for the shared skills vendored from
[`cwinters8/agent-skills`](https://github.com/cwinters8/agent-skills). The skills
are generic; the project-specific facts they act on are here.

AGENTS.md remains this project's single source of truth. Where this file
summarizes it, AGENTS.md wins on any disagreement.

## Rules source

`AGENTS.md` at the repo root. `CLAUDE.md` is a pointer that `@`-imports it and
holds no rules of its own.

## Repo

`cwinters8/sprite-locker` — **private**, single maintainer. The routine
reviewers are Codex and the `code-review` skill, both posting through known
identities. `review-sweep`'s reaction-count approval shortcut is permitted on
that basis; revisit it if the repo goes public or gains collaborators.

## Review focus

- **Locker sync invariants** — `utils/locker.ts` (`LockerEntry`, `reconcile`,
  `confirmWrite`) and the persistence effects in `App.tsx`. `pending` stays
  **derived** as `version > syncedVersion`, never stored or hand-cleared;
  locally-pending edits win reconciliation; cloud writes stay serialized through
  the single-writer worker. AGENTS.md → "Locker sync model" is authoritative.
- **Generated files** — `assets/sprites/index.ts` is regenerated by
  `scripts/vendor-sprites.mjs`. A hand-edit is a defect. Edit the catalog through
  `data/sprites.source.json`.
- **Vendored skills** — everything under `.claude/skills/` is vendored from
  `cwinters8/agent-skills`. A hand-edit there is a defect: fix it upstream and
  re-run `npm run skills:sync`, or put the project-specific correction in this
  file.
- **Client secrets** — only `EXPO_PUBLIC_*` values belong in client code.
- **App variants** — `app.config.js` gives `development` a distinct bundle id and
  scheme so the dev client and tester binaries coexist. Changes there are only
  observable after a prebuild per variant (AGENTS.md → App variants).

## Threat model

Sprite Locker ships the Supabase URL and anon key inside a public app binary
(`utils/supabase.ts`). Anyone who installs the app can extract both in minutes,
sign up for their own account, and call PostgREST directly with `curl` — no app,
no UI, no client code in the path. **Postgres Row Level Security is therefore the
only thing standing between one user and another user's rows.** Every client-side
guard in `App.tsx` — the session-id checks in the sync worker, the sign-out clear
— protects the honest user's own data from bugs, and constrains an attacker not
at all.

## Trust boundary

| Path | Groups |
| --- | --- |
| `supabase/**` | authorization, client-data |
| `utils/supabase.ts` | auth-session, secrets, client-data |
| `App.tsx` — auth, deep-link, or `syncLocker` code | authorization, auth-session, client-data |
| `App.tsx` — code rendering or consuming catalog fields | client-data |
| `app.json`, `app.config.js`, `eas.json` | auth-session, secrets, client-data, supply-chain, release |
| `.github/workflows/**`, `.eas/workflows/**`, `scripts/**` | supply-chain, secrets |
| `package.json`, `package-lock.json` | supply-chain, release |
| `.env*`, anything adding a `process.env` read | secrets |
| `data/sprites.source.json` — an added or changed `asset` value | supply-chain |
| `data/sprites.ts` | client-data |

The cross-group rows are deliberate, because the obvious row misses the actual
risk: an HTTP URL or an ATS / cleartext exception arrives through
`utils/supabase.ts`, `app.json`, or `data/sprites.ts` (the Fortnite.gg fallback
URL); a changed update project or channel arrives through app or EAS config; an
unconstrained new synced column arrives through a schema migration with no client
change at all; a transitively-added runtime permission or a widened CI secret
arrives through a dependency bump or a workflow edit.

`App.tsx` appears twice on purpose. Its auth/sync code is one trust surface; the
code that *renders* scraped catalog strings is a different one, and that risk is
introduced at the render site. A rendering change usually leaves
`data/sprites.ts` untouched, so without its own row it would match nothing.

Both workflow directories are in scope: `.eas/workflows/` builds and publishes
the app, so an edit there reaches users' devices exactly the way a
`.github/workflows/` edit reaches the repo.

A config diff runs only the permissions and encryption-declaration checks from
the release group; the rest is release-time and full-sweep only. A docs-only diff
needs none of this. A catalog diff is **not** automatically exempt: `asset`
filenames flow from scraped HTML into a path join, so a changed `asset` value is
routed to supply-chain even when no script changed.

## Stack

- `postgres-rls` — Supabase (Postgres + PostgREST), RLS-enforced.
- `ci-workflows` — GitHub Actions in `.github/workflows/`. `.eas/workflows/` is
  EAS Workflows and has no `permissions:` block to check; the rest of the module
  still applies to it.
- `mobile-release` — iOS App Store and Google Play via EAS.

## Identity model

- Email magic-link OTP via `signInWithOtp`, with `shouldCreateUser: true` — a
  deliberate signup-by-link decision, and ordinary app code in `App.tsx`, so a
  diff that changes it is a finding to catch by reading the diff.
- The client is configured `flowType: 'implicit'`, and `handleAuthUrl` reads
  `access_token` / `refresh_token` straight out of the callback URL.
  `exchangeCodeForSession` is already wired for a PKCE migration.
- Callback surfaces: `spritelocker://auth/callback` and
  `spritelocker-dev://auth/callback` — custom schemes, one per app variant
  (AGENTS.md → App variants, `SUPABASE_SETUP.md`). Both must be in Supabase's
  redirect allowlist. Expect an exact HTTPS callback on an owned domain to join
  them when the App Link migration lands; that addition satisfies the allowlist
  rule rather than violating it.
- Rows are owned by `user_id`; the primary key of `sprite_statuses` is
  `(user_id, sprite_id)`, so `sprite_id` alone never names a row. `status` is
  constrained by a CHECK constraint (`found` / `owned`), and `updated_at` is
  written by the `set_updated_at` trigger.
- Session tokens are stored in `AsyncStorage`.

## Secrets policy

- `EXPO_PUBLIC_*` is a promise about **visibility, not safety**: the prefix only
  means "inline this into the bundle". A service-role key placed in
  `EXPO_PUBLIC_SUPABASE_KEY` ships to every device, bypasses RLS entirely, and
  passes a naive grep. Verify the value: a legacy JWT-style key must decode to
  `"role": "anon"`, and a newer-style key must be `sb_publishable_…`, never
  `sb_secret_…`. Check every EAS build environment, not just local
  (`EAS_ENV_SETUP.md`); production is the one most likely to be set hastily.
- No service-role key anywhere in the repo or client, under any variable name.
- `.env*` is gitignored except `.env.example`, which carries placeholders only.
- `EXPO_TOKEN` publishes JavaScript to every installed build over EAS Update. It
  is the highest-value secret this project holds.

## Probe policy

Two-account PostgREST probing is permitted against the **development** Supabase
project, using accounts created for the purpose. Never probe production, and
never use a real user's token. Run the full probe set — including the
server-authoritative `updated_at` probes — before the first store submission.

## Known gaps

- **Implicit flow over custom schemes** (`flowType: 'implicit'`) — the callback
  carries real tokens over a scheme no domain proves ownership of. *Open; close
  before launch* by migrating to PKCE plus verified App Links / universal links.
- **`handleAuthUrl` accepts credentials from any inbound URL** — it does not
  check that the path is `/auth/callback` or that the URL arrived on an expected
  scheme. *Open.*
- **Session tokens in `AsyncStorage`** — unencrypted; readable on a rooted or
  jailbroken device and may land in backups. `expo-secure-store` is the right
  home. *Open, medium.*
- **`pr-preview-update.yml` puts `EXPO_TOKEN` in a job-level `env:`**, so it is
  present during `npm ci` and readable by any compromised install script. Move it
  onto the EAS setup and publish steps only. *Open — treat as a finding to fix,
  not an accepted arrangement.*
- **`asset` path traversal** — `scrape-sprites.mjs` lifts `asset` from scraped
  markup and validates only non-emptiness and uniqueness, and
  `vendor-sprites.mjs` then does `join(assetsDir, asset)` and interpolates the
  same value into a generated import. An `asset` containing `../` escapes
  `assets/sprites/`, and the whole attack arrives as a data-only diff. *Open;
  fix at both ends.*
- **No in-app account deletion** — the app creates accounts by magic link and
  offers only sign out. *Launch blocker* (App Store 5.1.1(v); Play has a parallel
  requirement).
